# 组件规范

本参考帮助选择组件、安排层级和补齐视觉状态。数值是无现有规范时的起点；品牌、暗色主题和项目已验证的组件库优先。先映射 [视觉变量](visual-system.md)，再读与任务有关的章节。

以下 HTML/CSS 均为局部片段，用于说明结构或样式，不是可以直接发布的完整组件。请求、校验、键盘行为和焦点管理需接入真实实现；详细行为见 [交互与可用性](interaction-and-accessibility.md)。

## 1. 按钮：先分清操作层级

| 角色 | 默认外观 | 适用情况 | 选择依据 |
| --- | --- | --- | --- |
| 主要操作 | `action` 底色、`text-on-action` 文字 | 保存、提交、开始下一阶段 | 当前任务希望用户完成的主要动作 |
| 次要操作 | `surface` 底色、`border-control` 描边 | 取消、预览、导入等辅助动作 | 与主要操作同屏，需保持清楚可见 |
| 轻量操作 | 透明背景、明确文字或图标 | 行内编辑、展开、更多 | 操作位置和上下文已能说明其可点击性 |
| 危险操作 | `danger-action` 强调，或有明确文案的危险次要按钮 | 删除、撤销权限等有后果的动作 | 按风险决定强调程度，不把红色用于普通强调 |

- 同一任务区通常突出一个主要操作；相互独立的任务区可以各有主要操作。不要为了控制数量降低真正重要动作的辨识度。
- 常规按钮高度从 40–44px、水平内边距从 16px、文字从 14–16px 起步；密集行内操作可收紧，触控场景适当扩大命中区。
- 使用 `radius-control`；图标与文字间隔从 8px 起步。内容长时允许合理换行或调整布局，不强制省略关键动作文字。

| 状态 | 默认处理 | 应避免 |
| --- | --- | --- |
| Hover | 主要按钮使用 `action-hover`；次要按钮轻填充 | 所有操作都放大、漂浮或改变位置 |
| Focus-visible | 清楚的外轮廓，轮廓与背景可辨 | 用 hover 代替键盘焦点 |
| Active | 可用轻微明暗变化确认按下 | 大幅缩放导致误点或布局跳动 |
| Disabled | 保留可辨文字，并在需要时说明条件 | 只靠降低透明度表达禁用，用户不知道原因 |
| Loading | 按钮内说明实际进度，保持尺寸稳定 | 显示“已保存”却仍在请求中，或可重复提交 |

```html
<button class="ui-button" type="submit">保存设置</button>
```

```css
.ui-button {
  min-block-size: 2.75rem;
  padding: .625rem 1rem;
  border: 1px solid transparent;
  border-radius: var(--mui-radius-control);
  background: var(--mui-action);
  color: var(--mui-text-on-action);
  font: inherit;
  cursor: pointer;
}
.ui-button:hover:not(:disabled) { background: var(--mui-action-hover); }
.ui-button:focus-visible {
  outline: 2px solid var(--mui-focus);
  outline-offset: 3px;
}
.ui-button:disabled { cursor: default; }
```

片段只展示主要按钮与焦点。禁用视觉和加载状态需由项目补齐；若使用 `aria-disabled` 保留可聚焦性，必须同时阻止执行并说明原因，它不会自动禁用按钮。

## 2. 卡片与分隔：表达分组，不把每段内容都装进盒子

| 用途 | 默认规格 | 选择依据 |
| --- | --- | --- |
| 普通内容卡片 | 16–24px 内边距，`radius-panel`，平面背景 | 信息确实属于独立对象或任务 |
| 数据密集区 | 较紧凑留白，必要时仅用分隔线 | 表格、日志、列表需要连续比较 |
| 可点击卡片 | 明确标题链接或主要入口，提供焦点和反馈 | 卡片代表可进入的实体 |
| 分区分隔 | 留白优先，必要时 1px `border-decorative` | 标明相邻组的边界，避免装饰过密 |

- 卡片标题、说明、内容、操作沿同一内容列对齐；内部间隔先从 8、12、16px 选择，区块间隔更大。
- 不默认叠加描边、阴影、渐变和顶部色条；需要区分浮层、选中或风险时再添加相应线索。
- 整张卡片点击时，避免在外层链接中嵌套按钮或链接。含多个操作时，优先让标题链接承担导航，独立按钮承担动作。
- 栅格可拉齐同组卡片高度，但不要为了对齐隐藏说明或固定死高度；长标题和窄屏仍应完整显示。
- 分隔线跟随信息结构：整行列表可贯穿，带头像或前导图标的列表可对齐正文。不要用空白字符模拟间距。

常见问题：卡片嵌套三四层后，边框比内容更醒目。优先去掉没有独立语义的外壳，保留标题、间距和必要分隔。

## 3. 输入框与字段组

| 元素 | 默认规格 | 处理要点 |
| --- | --- | --- |
| 字段标签 | 14px 起，控件上方，间隔约 8px | 保持可见并与控件关联 |
| 单行输入 | 40–44px 高度起点，12px 水平内边距 | `border-control`、`radius-control`，沿用系统或项目字体 |
| 多行输入 | 按任务设置初始行数，允许必要扩展 | 不把正文编辑限制为单行；长内容有明确滚动边界 |
| 帮助文字 | 14px 起，`text-secondary` | 输入前说明格式和限制，避免重复标签 |
| 错误文字 | `error-text` 与明确文字说明 | 与字段关联，必要时同时调整边框 |

```html
<div class="ui-field">
  <label for="project-name">项目名称</label>
  <input id="project-name" name="projectName" required
         aria-describedby="project-name-help">
  <p id="project-name-help">使用便于团队识别的名称。</p>
</div>
```

这是正常状态片段。发生错误时，更新 `aria-invalid` 并关联实际错误文本；不要长期挂着不存在的错误引用。

- Search、email、number 等类型按数据语义选择；电话号码、编号等不能因为包含数字就一律使用数值输入。
- 只读字段说明“可查看不可编辑”；禁用字段说明当前不可操作。需要复制的信息不应因禁用而难以选中。
- 前后缀、清除、显示密码等按钮留出独立位置，不能覆盖输入文字；图标按钮使用清楚的名称。
- 字段宽度体现内容特点：短编号可紧凑，地址和描述需要空间。不要为了网格齐整把所有字段拉成相同长度。
- 错误不只改变颜色；检验顺序、提交失败处理及输入法行为见 [表单行为](interaction-and-accessibility.md#forms)。

## 4. AI 输入容器与对话工具栏

输入容器适合“正文输入 + 附件/模式 + 发送”的任务。普通搜索无需套用复杂聊天框；仅有文本问答也不必预留一排无实际能力的工具。

| 区域 | 默认规格 | 处理要点 |
| --- | --- | --- |
| 外壳 | `radius-panel`，1px `border-control`，12–16px 内边距 | 外壳承担主要边界时，内部文本区可减轻边框 |
| 文本区 | 起始约 2–3 行，按内容增长至合理上限 | 超过上限内部滚动，保留编辑位置 |
| 附件区 | 文件名、状态和移除操作成组 | 区分上传中、失败、就绪，长文件名仍可识别 |
| 底部工具栏 | 8px 间隔，可换行，发送靠近输入 | 主要操作保持可达，窄屏不要压缩成无法辨认的图标 |
| 生成中状态 | 按真实能力展示停止或其他可用动作 | 不把停止按钮当装饰；停止后说明实际状态 |

```css
.ui-composer {
  padding: 1rem;
  border: 1px solid var(--mui-border-control);
  border-radius: var(--mui-radius-panel);
  background: var(--mui-surface);
}
.ui-composer__tools {
  display: flex;
  flex-wrap: wrap;
  align-items: center;
  gap: .5rem;
  margin-block-start: .75rem;
}
.ui-composer__send { margin-inline-start: auto; }
```

片段只负责容器布局。文本区仍需要标签、可见焦点、发送约定和组合输入保护；附件与请求管理由实际功能实现。

常见问题：输入框在生成时被清空且无法恢复、用户上滑后仍被强制拉到底部、每个流式字符都触发读屏公告。按 [对话输入行为](interaction-and-accessibility.md#conversation) 分别处理。

## 5. 简单弹窗与复杂弹窗

| 类型 | 默认尺寸起点 | 结构 | 何时选用 |
| --- | --- | --- | --- |
| 短确认 | 最大宽度约 24–28rem，自然高度 | 标题、后果说明、操作区 | 一次明确的确认或少量说明 |
| 简短编辑 | 最大宽度约 28–36rem | 标题、短表单、错误区、操作区 | 用户需要保留当前页面上下文 |
| 复杂任务 | 约 40–56rem，受视口限制 | 清楚的头部、可滚动主体和操作区 | 有必要的长表单或内容选择；否则考虑独立页面 |

- 所有尺寸都受可用空间约束，窄屏保留边缘留白；`radius-dialog` 是外壳起点，内边距从 24px 起步，小屏可减至 16px。
- 短弹窗不固定高度，不为对齐制造大块空白；长弹窗需要滚动时，尽量保持单一、清楚的滚动区域。
- 标题说明任务，描述说明对象、范围及后果；普通确认的按钮沿用任务层级，危险确认使用准确动作名称。
- 复杂弹窗底部固定操作时，为内容留出空间，并检查软键盘、放大文字和当前焦点。不要让错误信息被底栏遮住。
- X、“取消”、Esc 和遮罩各自对应明确关闭规则；有未保存内容时保护输入，仍提供可理解的退出路径。
- 模态必须真正管理焦点进入、Tab 范围、背景不可交互和关闭后焦点恢复。优先复用经过验证的组件；仅添加 ARIA 属性不能形成完整弹窗。

常见问题：为了“轻量”把复杂流程塞入连续嵌套弹窗。优先在当前弹窗内切换明确步骤，或改为独立页面，避免用户丢失所在位置。完整行为见 [弹窗与破坏性操作](interaction-and-accessibility.md#dialogs)。

## 6. 标签、状态徽标与筛选 chip

| 类型 | 默认外观 | 正确语义与行为 |
| --- | --- | --- |
| 只读标签 | 12–14px，轻底色，4–8px 水平内边距 | 普通文字；不添加手型或点击反馈 |
| 状态徽标 | 明确状态词，可配图形或状态色 | “待审核”“失败”等含义不能仅由颜色区分 |
| 可切换筛选 | 全圆或沿用控件圆角，留足命中区 | 按钮、复选框或单选语义依选择模型决定 |
| 可移除条件 | 条件文本 + 独立移除按钮 | 按钮名称包含移除对象，焦点有合理后继位置 |

- 独立开关型 chip 可用 `button` 与 `aria-pressed`；互斥选项优先复用单选组，不为统一外观丢掉选择语义。
- 选中状态可同时使用文字、勾选图形、边框或填色变化；暗色主题也应保持可辨。
- 筛选条件过多时提供清楚的已选区域和重置操作；明确“清除全部”影响哪些条件，不暗中重置其他页面设置。
- 标签短小是为了便于扫描，不能因此删掉区分业务状态所必需的词。

## 7. 链接与图标

| 元素 | 默认规格 | 选择依据 |
| --- | --- | --- |
| 文中链接 | 沿用文字字号，保留下划线等非颜色线索 | 导航到资源或位置，能与正文区分 |
| 独立导航链接 | 对齐项目导航样式，当前项有明确状态 | 菜单、目录、分页等已具导航上下文的区域 |
| 辅助图标 | 常用 16–20px，和文字视觉重量一致 | 补充动作或信息，已有文字时避免重复命名 |
| 主要图标按钮 | 图形约 20–24px，外围命中区适当扩大 | 高频且易理解的动作；陌生动作优先加文字 |

- 图标沿用同一主要体系，检查描边粗细、基线和光学大小，不只核对文件像素尺寸。
- 装饰图标从可访问名称中排除；无文字图标按钮必须有描述动作的名称，tooltip 可以补充但不是唯一命名来源。
- 下载、外链等提示在能帮助理解结果时保留；新窗口行为按产品约定明确告知，不把所有外部链接默认强制新开。
- 触发动作使用按钮，改变位置使用链接。不要用 `href="#"` 假扮保存，也不要把整段普通文字变成隐形点击区。

## 8. 表格工具栏与批量操作

| 区域 | 默认安排 | 处理要点 |
| --- | --- | --- |
| 标题与统计 | 标题靠近数据范围，统计为辅助信息 | 明确计数是总量、筛选后数量还是已选数量 |
| 搜索与筛选 | 常用条件直接显示，更多条件可收纳 | 回车或即时检索遵循现有约定，保留当前条件 |
| 页面操作 | 与筛选区区分，突出必要主要动作 | 新建、导入、导出文案具体，导出范围清楚 |
| 批量工具栏 | 选中后显示数量和可用动作 | 说明选中的是当前页还是全部结果 |

- 工具栏间隔从 8–12px 起步，分组间隔从 16–24px 起步；窄屏允许换行，重要操作不消失在水平溢出之外。
- 表格使用对应语义，表头和数据关系明确；可排序列以实际按钮提供操作，当前排序状态与数据一致。
- 数值可右对齐并使用等宽数字，文本靠起始侧；选择、图标、菜单等专用列可按内容居中，不强求所有列同一对齐方式。
- 行内菜单承载低频操作；关键且频繁使用的操作可直接显示。只显示在 hover 中的入口也应能由键盘发现和使用。
- 空结果保留筛选工具和恢复入口；加载刷新不要误显示“暂无数据”。固定表头或操作栏需检查焦点遮挡。

常见问题：批量操作出现后推走搜索栏，用户失去筛选上下文。预留稳定位置或在清楚的选中区展示操作，并保持已选数量可见。

## 9. 引导浮层与提示

| 类型 | 默认安排 | 选择依据 |
| --- | --- | --- |
| 普通 tooltip | 靠近目标，短说明，按空间避让 | 补充非必要信息，不承载按钮或必须阅读的正文 |
| 可交互提示卡 | 标题、短说明、必要操作，约 18–24rem 宽度起点 | 用户需要在浮层中做选择，按实际结构管理焦点 |
| 分步引导 | 当前步骤、目标说明、下一步与跳过 | 多步任务确实需要帮助，可退出并重新查看 |

- 浮层使用 `surface`、`text` 和 `radius-panel`，需要时添加轻边界或项目既有浮层阴影；遮罩不能使目标内容难以读清。
- 不把 hover 作为唯一触发方式；检查键盘、触屏、关闭行为和目标不存在时的回退路径。
- 普通 tooltip 不获取焦点或锁住 Tab；带按钮的提示不能继续冒充 tooltip。模态引导才采用模态行为，非模态引导保留周边操作。
- 浮层位置根据可用空间调整，长文案可换行；不要遮住目标控件、下一步按钮或当前焦点。
- 引导不是修补模糊界面的替代品。用户反复依赖引导才能完成同一任务时，先改进标签、布局和操作反馈。
