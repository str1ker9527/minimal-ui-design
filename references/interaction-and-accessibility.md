# 交互与可用性

极简界面仍需要回答四个问题：现在是什么状态、用户可以做什么、操作产生了什么结果、遇到问题如何继续。本篇用于表单、异步任务、弹窗、对话及受保护流程；组件外观和尺寸详见对应组件参考。

以下交互偏好可以按产品、设备和用户习惯调整。业务结果必须真实，可访问性要求不能用审美偏好替代。本文提供常见实现与验收方法，不代表完整 WCAG 合规清单。

## 1. 先确定动作和结果

同一功能先定义成功条件，再选择按钮和提示。例如“保存草稿”只保存可继续编辑的内容；“提交审批”进入实际审批流程；“发布”使内容达到产品定义的可见范围。这些动作不能共用模糊的“完成”掩盖差异。

| 判断点 | 设计决策 | 典型场景 |
| --- | --- | --- |
| 改变当前页面或打开资源 | 使用链接，保留正常导航能力 | 查看详情、打开帮助 |
| 修改数据或当前界面状态 | 使用按钮，并表达当前是否可操作 | 保存设置、展开筛选 |
| 后果轻、容易恢复 | 通常直接执行，必要时提供实际可用的撤销 | 调整排序、取消收藏 |
| 影响大或难以恢复 | 执行前解释对象、范围与后果 | 删除团队、替换已有配置 |
| 完成依赖服务返回 | 先表示处理中，再按实际结果更新 | 上传、提交、导出 |

- 按钮说明动作及必要对象，例如“保存设置”“导出报表”。上下文已明确时，“保存”“下一步”“取消”可以成立。
- 一个任务区应有清楚的主要动作；存在多个独立任务区时，各自可以有主要动作，不限制为全站只能有一个主按钮。
- 禁用动作时让用户知道缺少什么条件，避免只能看见灰色按钮、找不到原因。解释放在相邻位置，不仅藏在禁用控件的 hover 中。
- 可点击区域使用合适的交互语义，避免仅给普通文本或容器添加点击事件。只读信息不呈现成可操作控件。

**文案示例：** “确定”不一定错误，但删除确认中的“删除 3 个文件”更清楚；“操作成功”可以改成实际结果，例如“设置已保存”。不能把“请求已受理”写成“导出完成”。

## 2. 加载、提交与长任务

### 选择与任务对应的反馈

| 当前情况 | 合适的反馈 | 应保留的能力 |
| --- | --- | --- |
| 单个按钮触发短请求 | 按钮内显示进行中，处理重复提交 | 保留页面内容与其他无关操作 |
| 正在获取结构已知的内容区 | 局部骨架或内容区加载提示 | 保留导航及已经可用的内容 |
| 刷新已有列表 | 保留旧内容并说明正在更新 | 区分旧内容与最新结果，避免误认已刷新 |
| 已知真实总量的任务 | 根据实际完成量显示进度 | 说明处理对象，处理失败或中断 |
| 无法知道总量的任务 | 不定进度与简短状态文字 | 有实际能力时提供取消或稍后查看 |

- 请求开始即记录真实 pending 状态，防止重复请求造成重复记录。快速请求可短暂延迟 loading 的视觉呈现以减少闪烁，但不能因此缺少提交保护。
- 不为展示骨架而延迟已经就绪的内容，也不按固定秒数机械更换一整套反馈组件。
- 有真实总量才能显示百分比，有真实阶段才能显示阶段；进度未知时不伪造倒计时、处理条数或流式输出。
- 状态应属于对应任务，避免保存一个字段导致整页不可操作。确有一致性要求时再锁定相关区域，并说明原因。
- 搜索、筛选或切换对象时，较早请求的返回不能覆盖用户较新的选择。取消本地等待不等于服务端已经停止，界面文案要符合实际能力。
- 长任务只有在确实支持时才提供“关闭页面后继续”或“后台运行”；取消、重试、稍后查看也应对应可用功能。

### 完成与失败之后

成功后让结果留在用户能确认的位置：保存状态更新、列表出现新记录、下载入口可用，或导航到明确结果页。轻量 toast 可以补充反馈，但不能代替需要持续查看的结果。

失败时恢复适当操作能力并保留可恢复输入。网络中断后无法确定是否提交成功的操作，应先核对结果或使用项目已有防重机制，避免直接重试造成重复提交。

自动保存应区分“正在保存”“已保存”和“保存失败”。若只保存到当前设备，不写成已经同步；离开页面是否会丢失内容，按实际存储和恢复能力说明。

## 3. 空状态与错误恢复

空白区域不是单一状态。先判断为何没有内容，再给用户一条相关路径。

| 场景 | 应说明什么 | 可提供的下一步 |
| --- | --- | --- |
| 第一次使用，尚未创建内容 | 这里将展示什么、创建后有什么用 | 创建第一项；必要时查看示例 |
| 筛选或搜索后无结果 | 当前条件没有匹配项 | 修改条件、清除筛选 |
| 数据确实为空但无需用户处理 | 当前没有待处理内容 | 保留正常导航，不强加创建动作 |
| 无权查看 | 当前账号无法访问该范围 | 有真实流程时申请权限或切换账号 |
| 获取失败 | 内容暂未加载出来 | 重试、返回；有依据时提供帮助入口 |

不要用“暂无数据”遮盖请求失败，也不要在无权限时诱导用户反复刷新。保留搜索词和筛选条件，让用户能知道无结果是如何产生的。

- 错误尽量靠近来源：字段错误放在字段旁，表单提交错误放在表单区域，整页加载失败放在主体区域。
- 重要错误需要可持续查看的载体；短暂 toast 不作为唯一提示。多个相关字段同时出错时，可以提供错误摘要并连接到相应字段。
- 说明已知问题和可执行的恢复动作。原因未知时承认失败，不猜测“网络异常”“服务器维护”或用户操作错误。
- “已收到错误报告”“预计 5 分钟恢复”“请联系管理员”等说法必须有真实流程或事实依据。
- 给普通用户可理解的说明；技术用户需要时可提供安全的错误码或诊断入口，不暴露凭据、内部堆栈或敏感数据。

**差：** “异常！请重试。”

**更清楚：** “本次保存未完成。已保留你填写的内容，可以再次保存。”仅在确实保留输入、允许重试且不会重复提交时使用这段说明。

## 4. 表单：输入之前、之中和之后

### 字段和帮助信息

- 普通字段使用持续可见且关联的 label；placeholder 用于例子或补充提示，不承担唯一标签。特殊紧凑控件仍需可访问名称。
- 输入前说明必填项、格式或影响任务的重要限制。可用“可选”标出少量可选项，也可标必填项，但同一表单采用一致方式。
- 示例必须帮助理解格式，不让用户误以为已有真实值。默认值应有业务依据，尤其避免默认勾选会产生费用、授权或其他重大后果的选项。
- 选择控件应匹配选择方式：单选与多选不能混淆；选项很多时依据检索需求使用搜索或分组，沿用现有组件及键盘行为。
- 对明显相关的字段分组并说明共同用途，例如“账单地址”。不要仅因字段数量增加而拆成多步，先看用户是否需要分阶段决策。

### 校验时机

| 时机 | 默认处理 | 需要调整的情况 |
| --- | --- | --- |
| 刚打开表单 | 呈现标签、帮助和限制，不先铺满错误 | 已有未完成记录需要显式提示时 |
| 首次填写字段 | 通常在完成输入或离开字段后校验 | 字符计数、密码强度等可即时提示 |
| 已报错后修改 | 重新校验相关条件，及时清除已解决错误 | 依赖服务端的校验需处理等待状态 |
| 提交 | 检查所有必填与相关约束，阻止无效提交 | 服务端仍需执行其负责的校验 |

- 不在用户尚未输入完整邮箱或日期时不断报错。即时反馈有帮助时使用，避免错误消息随每次按键反复出现和消失。
- 原生表单元素优先使用 `required` 等能力；自定义校验需与项目现有机制协调，不叠出两套互相矛盾的错误提示。
- 错误时用 `aria-invalid` 标识无效状态，并通过 `aria-describedby` 等方式关联帮助或错误文本；错误解决后同步更新这些状态。
- 错误文字指出问题与修正方式，例如“结束日期不能早于开始日期”。不能只把边框变红，也不能要求用户猜测“格式错误”是哪种格式。

### 提交与键盘输入

提交失败时保留仍可安全保留的输入，必要时聚焦错误摘要或首个错误字段，让用户能够继续修正。只因某个字段不合法就清空整张表单，会把小问题变成重新填写任务。

Enter 提交或键盘快捷键必须保护输入法组合输入：中文等语言选词时的 Enter 不应触发提交。使用框架和事件提供的组合输入状态，例如 `isComposing`，并在实际输入法中验证，而不是仅用英文输入验证按键逻辑。

默认采用顺畅的单列阅读路径；相关短字段可以成组。固定提交区要为内容留出空间，并实测窄屏、页面滚动和软键盘打开后的焦点位置。

**场景：** 用户提交一张较长申请表后，发现底部必填项缺失。界面应让用户定位到具体字段并保留前面的填写内容；页面顶部短暂显示“提交失败”不足以帮助完成任务。

## 5. 弹窗与破坏性操作

### 先决定是否需要弹窗

短确认和需要保留当前上下文的小任务适合弹窗。长表单、多步操作、需要频繁对照其他内容的任务，可以选择侧栏或独立页面，按产品现有模式决定，不强行把所有操作装进模态弹窗。

短确认弹窗随内容自然高度；长内容才考虑分区和内部滚动。需适应小屏和软键盘，不统一强制某个视口高度。标题、说明和动作在长文案下仍应可达。

### 模态行为

优先复用已有可访问弹窗组件或正确实现的原生 dialog；只添加 `role="dialog"` 不代表行为完整。真正的模态弹窗应做到：

- 有可访问名称；打开后焦点进入与任务相符的位置，Tab 保持在模态内容内，背景不能继续交互。
- 通常支持 Esc 取消关闭；Esc 不执行确认动作。关闭后焦点返回触发元素，或在该元素已不存在时移到合理后继位置。
- X 与“取消”可以并存，按组件体系和场景选择。无论如何都应有清楚的取消路径，避免把用户困在弹窗里。
- 点击遮罩关闭是可选设计。存在未保存输入或高代价操作时防止误触；关闭前有必要保护内容时，说明将发生什么。
- 初始焦点按内容理解与操作风险决定；不可逆确认可先放在取消等较安全操作上，不机械聚焦最醒目的按钮。

### 删除与恢复的决策

| 操作特征 | 默认处理 | 必须说明的内容 |
| --- | --- | --- |
| 低风险且确有撤销能力 | 可以直接执行并提供撤销 | 操作对象，以及撤销入口 |
| 可恢复但影响较大 | 通常先确认，按实际机制提供恢复入口 | 影响范围、真实恢复条件 |
| 不可恢复或有重大连带影响 | 执行前明确确认 | 对象、范围、已知后果 |
| 批量操作 | 显示数量，必要时提供所选对象预览 | 本次选择范围及部分失败的结果 |

不虚构“不可撤销”“30 天内恢复”或服务端已有回收站。要求用户输入名称等额外摩擦，只在减少误操作确有价值时采用，不作为所有删除动作的统一规则。

确认后仍要处理进行中、失败与成功。失败不能直接关闭并显示“已删除”；批量部分成功时分别说明成功和未完成的范围，保留继续处理的路径。

**示例：** “删除所选 3 个文件？”比“你确定吗？”信息更充分。若恢复能力尚未确认，先核实产品实际行为，不用猜测性后果补全文案。

## 6. 对话输入与首次引导

### 对话与生成过程

- 输入区需要可见标签或可访问名称，并清楚区分发送、发送中、停止和重试。窄屏允许工具栏换行，不把必要操作挤出可见范围。
- 明确 Enter 和换行的方式，沿用产品既有快捷键习惯并提供可发现提示；同样遵循表单章节的输入法组合输入保护。
- 真实流式内容按实际到达更新，不通过预制文字假装处理过程。演示数据仅用于明确标识的演示场景。
- 自动滚动不应强行打断用户阅读历史内容。用户离开底部阅读时，可用“有新内容”等入口帮助返回，按实际新增状态显示。
- 中断、失败和用户停止应有不同含义；停止后已有内容是否保留、重试是否重新生成，按产品真实行为说明。
- 对辅助技术的状态公告控制频率，可以在阶段变化或整条消息完成时提示，避免每个字符都触发 live region。确需 log 模式时检查实际读屏表现。

### 引导与渐进提示

首次引导应围绕当前任务，允许跳过并重新查看。成熟功能不因用户未完成引导就一直遮挡操作，除非确有必须完成的设置条件。

普通 tooltip 不使用模态焦点锁。带交互的引导按实际模态性管理焦点，让跳过、说明及目标操作都可达；引导目标被隐藏或不在当前页面时，先恢复合理上下文。

聚光、高亮和动效在关闭动画后仍需静态定位线索。引导气泡不能溢出视口或遮住下一步操作；移动端和缩放后也要检查定位。

## 7. 登录、会话与权限

| 情况 | 应呈现的状态 | 继续路径 |
| --- | --- | --- |
| 尚未登录 | 当前功能需要登录 | 登录后回到获准目标 |
| 会话过期 | 说明需要重新验证身份 | 按项目机制续期或重新登录 |
| 已登录但没有权限 | 说明当前账号无法执行或访问 | 有实际流程时申请权限或切换账号 |
| 服务失败、原因不明 | 按请求失败处理 | 重试或提供已存在的帮助方式 |

使用项目既有身份处理机制。有刷新会话流程时先遵循该流程，不在组件里看到一个错误就清空全部状态，也不把所有服务错误都当作登录过期。

登录后回到获准的原目标；返回地址须限制在可信站内路径或项目允许列表内，不能直接信任任意 `next` URL。重新登录前保护尚未提交、适合保留的输入，避免用户恢复身份后必须从头开始。

隐藏按钮只能改善界面，实际权限仍由服务端控制。对于用户应该了解但暂不可用的能力，可以保留入口并解释原因；涉及敏感资源时按现有访问策略处理，不擅自展示信息。

## 8. 文案与本地化

文案先准确表达状态，再追求简短。沿用产品已有语气和人称，不把“你”“您”、拟人表达或某种标点设为通用规则。

- 同一个动作使用同一个名称，例如不要在入口叫“保存”、确认时叫“提交”、结果里叫“发布”，除非确有三个不同步骤。
- 以用户理解的对象命名，必要的技术术语保留并解释；少用“异常”“非法”“参数错误”等无法指导普通用户的内部表达。
- 日期、时间、数字和单位沿用目标语言与地区约定；涉及截止时间或跨时区协作时，明确实际使用的时区，避免只显示含义不明的本地时间。
- 为翻译后的长文案保留空间。关键操作不因固定宽度被截成省略号，错误和帮助文字允许合理换行。
- 不通过拼接零散词语假设所有语言的语序相同；优先使用项目已有本地化机制，数量、对象名称和状态作为其支持的参数处理。
- 状态不能只靠颜色、图标形状或位置传达。配上必要文字或可访问名称，让不同感知和操作方式的用户都能理解。

**示例：** “连接失败，请检查网络”仅在确实确定是连接问题时成立。原因未知时，“未能获取最新数据，可以重试”更准确；不要为了显得贴心而编造原因或恢复时间。

## 9. 可用性标准与实现边界

| 项目 | 实现要求与边界 | 官方依据 |
| --- | --- | --- |
| 文字对比 | 普通文字至少 4.5:1；符合标准定义的大号文字可为 3:1。测量实际前景/背景组合，不按 token 名称判断 | [WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| 必要非文本线索 | 识别控件及状态所必需的视觉信息通常需要对相邻色至少 3:1；纯装饰线与必要控件边界不能混为一谈 | [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) |
| 焦点 | 键盘焦点可见；原生 outline 或经过验证的自定义样式均可。移除默认轮廓时必须保留有效替代；不要求各浏览器外观相同 | [WCAG 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) |
| 焦点遮挡 | 当前焦点不能被作者创建的内容完全遮住；固定栏、浮层和软键盘场景需实测，尽量使整个控件清楚可见 | [WCAG 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) |
| 键盘 | 交互功能可用键盘完成，依赖轨迹输入等例外按标准判断；复杂组件遵循其相应键盘模式，不要求每个子项都单独进入 Tab 序列 | [WCAG 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)、[APG Patterns](https://www.w3.org/WAI/ARIA/apg/patterns/) |
| 点击目标 | WCAG 2.2 AA 的 2.5.8 以 24×24 CSS px 为基本目标，含间距、行内等例外；触控优先时以约 44×44 或更大为舒适起点，二者不能混称同一个硬指标 | [WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) |
| 减少动态效果 | 尊重 `prefers-reduced-motion`，使用静态替代或减少非必要动画；可作为产品默认要求，对应 2.3.3 为 AAA | [WCAG 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) |
| 缩放与重排 | 普通内容在窄至 320 CSS px 等效宽度时能重排，确需二维布局的内容有例外；检查文字放大、长内容及横向溢出 | [WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) |

按钮和链接使用合适的原生语义；图标按钮提供有意义的名称，有可见文字时避免可访问名称与其冲突。弹窗焦点和关闭行为参照 [APG Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。

不要为减少动态效果而全局强制所有动画变成 0.01ms：这可能影响依赖动画事件的逻辑，也不能处理 JavaScript 动画。按组件关闭位移、视差、闪烁等非必要效果，确保信息和操作仍保留。

## 10. 按任务验收

选择本次实际涉及的路径检查，不要求为了小改动测试无关模块。验收记录要区分已在运行界面验证的结果和静态检查得到的判断。

| 验收路径 | 观察重点 |
| --- | --- |
| 正常完成主要任务 | 动作名称、提交状态和真实结果一致，用户能确认结果 |
| 输入缺失或格式错误 | 错误可定位、可理解，已填内容保留，修正后错误消除 |
| 慢请求、失败与重试 | 无伪造进度，无重复提交，旧请求不覆盖新选择 |
| 空数据和筛选无结果 | 原因区分正确，下一步与当前状态相关 |
| 键盘完成流程 | 焦点可见且顺序合理，弹窗可进入、取消并返回 |
| 中文输入法与长文本 | 选词不误提交，换行与快捷键符合说明，关键文案完整 |
| 窄屏、放大与软键盘 | 当前输入、帮助信息和必要操作可达，固定区域不完全遮住焦点 |
| 有权限、无权限与会话变化 | 状态准确，恢复路径有效，不因界面隐藏就假定安全 |
| 减少动态效果与必要读屏路径 | 无动效仍能理解状态，名称和公告可理解且不过度重复 |

用真实可运行界面完成相关检查；涉及自定义复杂控件时补充对应键盘和辅助技术验证。自动检查可以发现部分问题，但不能单独证明交互可用或达到完整无障碍合规。
